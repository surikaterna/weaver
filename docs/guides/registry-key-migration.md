# Migrating a custom persistent schema registry key

The schema-required server stores registry metadata only at the protected storage key `_weaver.registry.schemas`. `createPersistentSchemaRegistry` accepts an omitted `key` or that exact string. Previously configured custom keys, including public config paths and alternate spellings of the protected key, now fail before registry hydration or binding. A registry document at a public key could previously be read as ordinary configuration.

Before starting the stricter server, inventory deployed registry `key` settings and provider data across environments, layers, and scopes. If any deployment used a custom key, **abort the rollout** until the following maintenance migration is complete. Removing the old option without migrating is unsafe: the canonical key may appear fresh and empty; Weaver does not search stored values for an old registry. Public reads of historical custom-key data are not guaranteed; their behavior is undefined under the stricter server. Do not rely on the new constructor to erase, hide, or discover that data.

1. Restrict access to the affected service and take a restorable backup of provider data, registry metadata, and the configuration identifying the old key. Keep public reads disabled or restricted during repair if the old key is publicly addressable.
2. With the service offline, inventory and export the **known** old key using an authorized, audited, read-only maintenance process. Do not pass that key to a live `createPersistentSchemaRegistry` call, and do not infer it from arbitrary stored content.
3. Validate the exported registry document, its schema graph, environments, registered service and fragment identities, and slot metadata. Stop on missing, corrupt, or conflicting data. Under authorized maintenance controls, write the validated document to `_weaver.registry.schemas`; do not use a public configuration write or change other stored values.
4. Configure the new server to omit `key` or supply `_weaver.registry.schemas` exactly. Start with a new config service on the repaired provider, verify registration identities and representative reads and writes, and confirm public `get`, namespace, inspection, REST, and SCOMP views do not expose the protected registry. Separately verify the old data against the backup before planning an audited offline removal; no automatic deletion occurs.

If validation or restart fails, stop the rollout and restore the backup under maintenance controls. A rollback to older code can reopen schemaless writes and custom-key disclosure; coordinate it with access restrictions. This procedure does not promise cross-process transactionality or perform any provider-specific repair automatically.
